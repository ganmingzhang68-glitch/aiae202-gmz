先说清楚：框架替你做了什么

上周 create_agent 一行就出来一个智能体。不用框架、裸用 openai 包，右边这些都得自己写：

  1. 把函数手写成 JSON 签名发给模型
  2. 解析 tool_calls，json.loads 参数，找函数执行
  3. 结果按 role="tool" 带上 tool_call_id 追加回去
  4. 写循环，直到模型不再调工具，还要防无限调
  5. 多轮对话，自己保存、回放整段历史
tools = [{"type": "function", "function": { # ① "name": "check_availability", "description": "Check if a destination is bookable.", "parameters": {"type": "object", "properties": {"destination": {"type": "string"}}, "required": ["destination"]}}}] history = [{"role": "user", "content": question}] # ⑤ for _ in range(10): # ④ msg = client.chat.completions.create( model=MODEL, messages=history, tools=tools).choices[0].message history.append(msg) if not msg.tool_calls: break for call in msg.tool_calls: # ② args = json.loads(call.function.arguments) history.append({"role": "tool", # ③ "tool_call_id": call.id, "content": check_availability(**args)}) print(msg.content)

每一条都不难，但每一条都会出错。右边二十行，用框架就是 create_agent(llm, tools=[check_availability]) 一行——框架把这些共性的事标准化了，你只管写工具、提示词、流程。今天先看它在生态里站在哪、里面长什么样，再看演示，最后拆成四块积木对到代码上。

10–12 min

架构图一：create_agent 里面长什么样

框架替你做的那几件事，拼起来就是这张图。左边三样是你写的，中间那一圈是框架替你跑的：问模型 → 模型要求调工具 → 执行 → 结果回填 → 再问，直到模型只回纯文本才退出循环。上周那行 create_agent(llm, tools=[...])，编译出来就是这张图。

两个细节记一下：工具的 schema 是发给模型看的，函数本身在 tools 节点里执行——模型从头到尾没碰过你的代码，它只是提了个要求；checkpointer 挂在整张图下面，它存的是消息历史，所以下一轮那几条 ToolMessage 会原样回来，这就是"记忆"的全部。

12–14 min

架构图二：LangGraph 把流程画出来

LLM 在节点里面：① ④ 的函数体里写了 llm.invoke(...)，② ③ 一行模型调用都没有，图本身只认函数。下一步去哪由边决定：route() 是你写的 if，读 State 里的 date、budget 选路；模型只能通过 ① 写进 State 的字段间接影响路线。State 是共用白板，checkpointer 给它存档，所以 interrupt() 停得住、接得上。

回看上一张图：create_agent 就是这张图的特例——只有 model、tools 两个节点，条件边只问"最后一条 AIMessage 有没有 tool_calls"。第 8 周换成 StateGraph 时，工具、模型客户端、检查点存储器一行都不用改。

架构图三：自主执行那一侧，以 OpenClaw 为例

对照上一张图，差别一眼就看出来：这里没有图——没有节点、没有边，Agent 拿到目标自己决定下一步；流程写在 Skills 和提示词里，不在代码结构里。

三张图看完，往上退一步：它们背后其实只有两种想法。

两边的差别只有一句话：流程是谁定的。左边是你把步骤画成图，模型只在节点里干活，所以每一步都能看、能测、能回放；右边是你给一个目标，模型自己拆任务、自己挑工具、自己决定下一步，能力上限高，但出了问题很难说清"它为什么这么做"。右边这一列，就是上一页那张 OpenClaw 架构图。

这门课两条路都会碰到：create_agent 让模型自己选工具，已经是"自主"那一侧的最小版本；第 8 周的 StateGraph 则是"显式 Graph"那一侧。真正的取舍不在框架名字上，而在这一步能不能交给模型决定——能就交，不能就画进图里。

同一套技术栈里的三个层次，怎么选

方式关注点核心概念用在
裸用 OpenAI 兼容 SDK直接调模型聊天补全、自己解析工具调用、自己写循环单次调用、实验、完全自定义的循环

模型客户端：供应商是配置项，不是代码

llm = ChatOpenAI( model=os.environ["LLM_MODEL"], base_url=os.environ["LLM_BASE_URL"], api_key=os.environ["LLM_API_KEY"], extra_body=json.loads(os.environ.get("LLM_EXTRA_BODY") or "null"), ) 模型客户端已就绪：deepseek-v4-pro @ https://api.deepseek.com/v1

ChatOpenAI 讲的是 OpenAI Chat Completions 协议，所以同一份代码能跑在 DeepSeek、OpenAI、本地 Ollama 或任何兼容接口上。它不知道什么是循环、什么是对话——那是上面一层的事。

LLM_EXTRA_BODY 是给服务商的私货：对 DeepSeek 来说它关掉思考模式。今天用不到结构化输出，但下周就要靠它了，现在别删。

notebook 开头那段 missing = [...] 检查，是为了缺变量时报一句人话，而不是在 ChatOpenAI 里报一堆看不懂的错。你们自己的 notebook 也照抄。

34–38 min

工具：这次参数有了说明

from typing import Annotated @tool def check_destination_availability( destination: Annotated[str, "要查询是否可预订的目的地"] ) -> str: """查询某个度假目的地当前是否可以预订。""" available = {"成都": True, "西安": True, "哈尔滨": False, "三亚": True, "拉萨": False} is_available = available.get(destination, False) return f"{destination}{'可以预订' if is_available else '暂不可预订'}。"

和上周比多了一样东西：Annotated[str, "..."]。模型拿到的 schema 里，每个参数都会带上这句描述——它就是靠这句话决定该往 destination 里填什么。上周有同学的工具参数被模型乱填，多半就是缺这个。

再看返回值：查不到的目的地返回 "……暂不可预订。"，而不是 None。工具的返回值是给模型读的一条消息，一定要是模型读得懂的一句话。

41–46 min

记忆是怎么来的：检查点存储器 + 线程

检查点存储器（checkpointer）在每一步之后把消息历史存一份，键是 thread_id。线程（thread）就是它记住的一段对话。你用一个配置字典选线程，作为 invoke 的第二个参数传进去：

session = {"configurable": {"thread_id": "travel-availability-1"}} result = agent.invoke({"messages": [{"role": "user", "content": "成都、西安、哈尔滨、三亚和拉萨，哪些可以预订？"}]}, session) result = agent.invoke({"messages": [{"role": "user", "content": "我想去暖和一点的地方，有哪些可以订？"}]}, session) 智能体：根据您的需求，想要去暖和一点的地方，可以预订并符合的是 **三亚**。 三亚位于海南岛，属于热带海洋性气候，冬季温暖宜人……

第二轮用户没说过任何城市名，模型却知道哪些可订、哪些不可订——因为检查点存储器把第一轮的五次工具调用和结果原样回放给了它。

规则只有两条：传同一个 id，接着上次说；传一个新 id，从头开始。

46–49 min

数一数消息：一次 invoke 和一条线程的区别

看运行记录时，最快判断"记忆有没有生效"的办法是数 result["messages"] 有几条。以刚才那两轮为例：

# 第一轮结束时，这条线程上有 8 条 HumanMessage 成都、西安、哈尔滨、三亚和拉萨，哪些可以预订？ AIMessage tool_calls=[check_destination_availability ×5] <- 一条消息里五次调用 ToolMessage ×5 成都可以预订。……拉萨暂不可预订。 <- 每次调用各一条结果 AIMessage 查询结果如下：✅ 可以预订：成都、西安、三亚 …… # 第二轮结束时，同一条线程上有 10 条：上面 8 条 + 新的一问一答 HumanMessage 我想去暖和一点的地方，有哪些可以订？ AIMessage 根据您的需求，想要去暖和一点的地方，可以预订并符合的是三亚 ……

三个结论：invoke 返回的是整条线程的历史，不只是这一轮；模型第二轮没再调工具，是因为五条 ToolMessage 已经在上下文里；要是第二轮打出来的第一条就是"我想去暖和一点的地方"，说明记忆没接上——光数条数还不够，练习二会亲手做出这种情况。

数字会因模型而异：有的模型会把五次调用拆成五条 AIMessage，一轮就是 12 条。数的方法不变。

49–51 min

记忆存在哪、存了什么、什么时候没了

问题答案
存了什么这条线程的全部消息：用户的话、模型的工具调用、工具结果、回复，一条不少
存在哪InMemorySaver——Python 进程的内存里
什么时候没了内核一重启就全没了；换一个新的 InMemorySaver() 实例也等于全没了
多个用户怎么办一人一个 thread_id，同一个存储器里互不串台
要跨重启、跨进程换持久化的检查点存储器，第 13 周讲

回到主线第一条——用户看得懂。检查点存储器不只是记忆，它还是一份现成的完整运行记录：智能体在这条线程上做过的每一步都在里面。你们批注运行记录时要的东西，框架已经替你留好了。

51–54 min

另一种"记忆"：工具自己带状态

_last_destination: str | None = None @tool def get_random_destination() -> str: """随机提供一个度假目的地。""" global _last_destination available = _DESTINATIONS.copy() if _last_destination and len(available) > 1: available.remove(_last_destination) destination = random.choice(available) _last_destination = destination return destination

这个工具记住上一次选了哪，保证连续两次绝不重复——用户说"不喜欢，换一个"时很有用。但它和检查点存储器是两回事：

检查点存储器工具里的 global
记的是消息历史你自己定义的任何变量
按谁隔离thread_id，一人一份不隔离——整个进程共享，用户 A 选过的会影响用户 B
模型看得见吗看得见，每轮回放看不见，只看到返回值

注意 .copy()：漏了它，remove 会把模块级列表越删越短。

stream_mode="messages" 每来一块就给你一对 (token, metadata)；metadata["langgraph_node"] 告诉你这一块是哪个节点产生的。模型节点的打出来，工具节点的换行——所以输出里"让我先随机挑选一个目的地"和"恭喜！"之间那行 ===，就是工具跑了一次的痕迹。

两轮共用一个 thread_id，所以第二轮模型知道被否决的是喀什，工具也保证不再抽到它。

这几种写法，看到就要停一下

  • 每次调用都新建智能体——把 create_agent(..., checkpointer=InMemorySaver()) 写进一个 ask(text) 函数里，每问一句造一个新存储器，记忆永远是空的。智能体建一次，反复 invoke。
  • thread_id 写死一个——所有用户共用 "conversation-1"，用户 A 的病历、订单会出现在用户 B 的上下文里。一人一线程。
  • 把工具里的 global 当记忆——它是进程级的、所有线程共享、重启就丢，模型还看不见它。对话记忆归检查点存储器管。
  • 有了检查点存储器还手工塞历史——把上一轮的回复再拼进这一轮的 messages，历史就重复了一遍，token 翻倍，模型也会被绕晕。
  • 上来就画 StateGraph——步骤明明能让模型自己决定，却先写了二十个节点。先 create_agent，不够用再升级。

InMemorySaver 名字里就写着"内存"。它够你做完这门课前 12 周的练习，但不是结课项目的记忆方案——第 13 周之前别把它当成能上线的东西。
